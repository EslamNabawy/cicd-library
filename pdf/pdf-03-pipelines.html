Runner checks out the commit, sets up a cached toolchain, runs build → test → scan (independent jobs in parallel, needs: for gates), and returns results as PR feedback. Fail-fast by default; advisory checks ride continue-on-error.

Stages & Builders

Hermetic · BuildKit · Kaniko

04 / The Three Verification Stages

  • Build — hermetic: pinned deps, clean env, no hidden host tools. Same commit → byte-identical output anywhere.
  • Test — unit (fast, per-PR) → integration → E2E/smoke (staging). PR suites stay under 10 min.
  • Security scan — npm audit, gitleaks, Trivy on every PR. Shifting left beats incident response.

05 / Without a Daemon: BuildKit & Kaniko

BuildKit (buildx)Kaniko
Needs daemonYes (local or remote)No — userspace build
Best inDocker agents, dev machinesLocked-down K8s
Secrets--secret mountsShort-lived tokens
RULE — BuildKit everywhere a daemon exists; Kaniko exactly where daemons are banned.
RUNNERS — managed = zero ops, cold caches (use registry/remote cache); self-hosted = warm cache, you own patches + scaling. Cache key must include lockfiles.
DAG — fan out independent jobs, gate fan-in; cap matrix axes; fail-fast for PR signal, advisory for experiments; retry idempotent steps only; quarantine flakes with owner + deadline.

Q: What belongs in the PR pipeline vs post-merge?
A: Fast unit/integration + scans in PR; slow E2E and staging gates post-merge.
