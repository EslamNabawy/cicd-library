Mechanism

Signals · Alerts · DORA

02 / How the Loop Runs

  • Every deploy labeled (version/SHA) so signals correlate with the change.
  • Dashboards track golden signals — latency, traffic, errors, saturation — plus business KPIs.
  • Alerts fire on symptom: error-budget burn, p99 spike. Never on every deploy.
  • Incident → revert or forward-fix → postmortem feeds new gates (test, scan, approval).

03 / The DORA Four

TRACK — deploy frequency · lead time for changes · change-fail rate · MTTR (mean time to recovery). DORA = DevOps Research & Assessment. SLOs (e.g. 99.9%) turn these into alerting budgets.
SLI → SLO → BUDGET — indicator (success ratio, p99) → objective (99.9%/30d) → error budget (allowed failures). Alert on burn rate: fast burn pages, slow burn tickets. Keep 3–5 SLOs per service, each with owner + runbook.
v1.4.2 deploys (SHA-labeled)
error rate 0.2% → 3.1% in 10 min (ALERT)
rollback to v1.4.1 (4 min, MTTR stops)
postmortem → new PR test (class of bug can't recur)

Discipline

Failures · Rules · Check

04 / Failure Modes

  • Alert fatigue (noisy thresholds) → alerts ignored; fix with SLO-based, actionable alerts.
  • Unlabeled deploys → can't tell which version broke prod; version-label everything.
  • Postmortems without pipeline changes → repeat incidents; every action item lands as a test, check, or runbook.
RULES — structured logs (key=value) + trace IDs + version labels from day one · PR results in minutes, anomalies in minutes, trends weekly.
Q: Logs vs metrics vs traces — one use each?
A: Logs: what happened. Metrics: how much/how fast. Traces: where a request traveled.
