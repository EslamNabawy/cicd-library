04 / Staging vs Production

STAGINGDEPLOY → VERIFY
rehearse · sanitized data · auto · smaller scale
PRODUCTIONAPPROVE → DEPLOY
serve users · real data · gated · full scale
  • Config drift → same chart/manifests, env-only values.
  • Approval bottleneck → policy gates for low-risk paths.
  • Rebuild instead of digest → pin digests end-to-end.
RULES — same digest staging → production · config from env vars/secrets, never code · small batches + feature flags · every deploy observable and reversible.

Choice

Delivery vs Deployment

02 / When Each

  • Delivery (human gate) — regulated industries, data migrations, coordinated launches, teams still building gate maturity.
  • Deployment (no gate) — SaaS with progressive delivery, strong SLOs, practiced rollback, trunk discipline. Start low-risk, expand as confidence compounds.

03 / Failure Modes

AUTOMATING A FLAKY PIPELINE ships bugs at machine speed — fix gates first, automate second. NO KILL CRITERIA lets bad releases reach 100% "successfully". NAIVE MIGRATIONS corrupt state — expand-contract only. ON-CALL DISTRUST re-adds manual gates — boring, practiced rollbacks build the confidence.
Q: The one-gate difference?
A: Delivery stages with human approval; Deployment promotes automatically. Same pipeline, different trust.

Release

Config · Trains

02 / Config vs Code

RULE — the artifact never changes between environments; everything else is config (env vars, secret stores, config maps). A staging-vs-production behavioral diff must be explainable by config diff alone — never by "we built it differently".

03 / Trains & Paths

  • Release train — scheduled departures; green + approved rides, the rest waits. Predictable for stakeholders, calming for on-call.
  • Promotion path — dev → preview → staging → production; skipping environments precedes incidents.
  • Hotfix lane — documented fast path (fewer approvals, same checks) for fires; used rarely, reviewed always.
  • Snowflake envs, real prod data in staging, and config baked into images are the three classic failures.

Practice

Drills · Postmortems

02 / Rollback vs Forward-Fix

ROLLBACK — cause unknown, blast radius growing, budget burning, fix uncertain. Default for Sev1. FORWARD-FIX — cause known, fix tiny and verified, rollback risky (migrations applied). DECIDER — on-call with pre-agreed thresholds, not a committee.

03 / Drills & Postmortems

  • Game days in staging; rollback rehearsals quarterly until MTTR is measured, not guessed.
  • Jenkins recovery: restore JENKINS_HOME backup, replay smoke pipeline.
  • Blameless postmortems where every action item becomes a test, check, alert, or runbook — or it recurs.
Q: Why old digests, never fresh builds?
A: The old digest is proven in production. A fresh build is an untested variable during an incident.

Mechanism

Signals · Alerts · DORA

02 / How the Loop Runs

  • Every deploy labeled (version/SHA) so signals correlate with the change.
  • Dashboards track golden signals — latency, traffic, errors, saturation — plus business KPIs.
  • Alerts fire on symptom: error-budget burn, p99 spike. Never on every deploy.
  • Incident → revert or forward-fix → postmortem feeds new gates (test, scan, approval).

03 / The DORA Four

TRACK — deploy frequency · lead time for changes · change-fail rate · MTTR (mean time to recovery). DORA = DevOps Research & Assessment. SLOs (e.g. 99.9%) turn these into alerting budgets.
SLI → SLO → BUDGET — indicator (success ratio, p99) → objective (99.9%/30d) → error budget (allowed failures). Alert on burn rate: fast burn pages, slow burn tickets. Keep 3–5 SLOs per service, each with owner + runbook.
v1.4.2 deploys (SHA-labeled)
error rate 0.2% → 3.1% in 10 min (ALERT)
rollback to v1.4.1 (4 min, MTTR stops)
postmortem → new PR test (class of bug can't recur)

CI/CD Systems   Chapter 06

Discipline

Failures · Rules · Check

04 / Failure Modes

  • Alert fatigue (noisy thresholds) → alerts ignored; fix with SLO-based, actionable alerts.
  • Unlabeled deploys → can't tell which version broke prod; version-label everything.
  • Postmortems without pipeline changes → repeat incidents; every action item lands as a test, check, or runbook.
RULES — structured logs (key=value) + trace IDs + version labels from day one · PR results in minutes, anomalies in minutes, trends weekly.
Q: Logs vs metrics vs traces — one use each?
A: Logs: what happened. Metrics: how much/how fast. Traces: where a request traveled.
