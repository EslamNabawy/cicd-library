ARTIFACTS

Picking up from Pipelines, where the build succeeded — we now follow the one thing that outlives the pipeline: the versioned, immutable artifact.

01 / Vocabulary

TermMeaning
ArtifactBuilt output + version (app:1.4.2, app:sha-9f3a)
RegistryStorage + distribution (Hub, GHCR, ECR, Nexus)
PromotionSame artifact approved staging → production (never rebuild)
DigestContent hash — the image's fingerprint

02 / Why Immutability

Rebuilding per environment means testing one binary and shipping another. Immutable artifacts guarantee what passed staging is what runs in production.

03 / Producer, Consumer, Lifecycle

PRODUCER build job → STORAGE registry → CONSUMER CD pipeline · Lifecycle: build → store → promote → deploy → retire.

04 / Commands

$ docker build -t ghcr.io/acme/app:sha-9f3a .
$ docker push ghcr.io/acme/app:sha-9f3a
$ docker tag ghcr.io/acme/app:sha-9f3a ghcr.io/acme/app:1.4.2 # promote: same digest, human tag
$ docker push ghcr.io/acme/app:1.4.2

05 / Versioning

  • Immutable primary tag: commit SHA — traceable, never overwritten.
  • Human tags: semver (MAJOR.MINOR.PATCH) applied at promotion, never rebuilt.
  • Never deploy :latest — it is unrepeatable.
  • Also valid: build numbers (build-1042) for ordering, date tags for nightlies. SHA always = truth.

Trust & Handoff

Failures · Signing · Next

06 / Failure Modes

  • Mutable tags overwritten → unreproducible deploys; fix with SHA digests + tag immutability.
  • Registry bloat/slow pulls; fix with retention + layer caching + regional mirrors.
  • Secrets baked into images; fix with multi-stage builds + secret mounts, scan with Trivy.

SUPPLY-CHAIN TRUST

Sign artifacts (cosign proves who built the image) and keep SBOMs (the machine-readable ingredient list) so a future CVE traces to exactly the affected images. Provenance attestations (SLSA-style) let consumers verify builder + commit before promoting.

Q: Why must the same digest flow through all environments?
A: Otherwise you tested one binary and shipped another — verification is void.
